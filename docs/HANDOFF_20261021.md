## 二、协议（改代码前必须理解）

### 1. 命令/事件通道

- 前端发命令：`sendCmd(action, payload)` → 经 WebView2 消息到 `WebShell.cs` 的大 if/else 链分发。
- 后端回执：**必须**调用 `ReplyOk(id, action)` 或 `ReplyFail(id, action, code, msg)`。

> **最致命的坑**：前端 `sendCmd` 会先把触发按钮置 `disabled + is-loading`，只有收到**同 id 的 res** 才恢复。
> 少一个回执，按钮永久卡住，整个界面"点不动"。本轮就因 `unlock.selectCard` 分支漏了 `ReplyOk` 导致界面锁死。

- 状态推送：后端 `PostToPage(json)`，`action` 形如 `dlss.state`、`unlock.state`、`settings.state`。

### 2. 手拼 JSON 的坑

后端大量用 `StringBuilder` 手拼 JSON（无序列化库）。
**拼错一个括号，前端 `JSON.parse` 抛错 → 整条消息被静默丢弃 → 界面毫无反应且极难排查。**

本轮真实事故：`sb.Append("]}")` + `sb.Append("}}")` 多了一个 `}`，导致 `settings.state` 从未生效。
已在 `HardwareBridge.SettingsStateEvt()` 加了首尾自检（`{`/`}` 与 `]}` 校验），拼错会抛异常进日志。**新写事件请照此加自检。**

### 3. 单一数据源 / 单一写入方

同一个 DOM 控件**只能有一个写入方**，同一个静态目录**只能由后端持有**。

本轮反复踩的坑（同一类问题 5 次）：

| 现象 | 根因 |
| :--- | :--- |
| DLSS 镜像下拉只有一个"默认镜像" | `renderDlssPage` 每次渲染重写 select，而我们另加的填充被覆盖 |
| 下拉框空白 | 标记里没有任何 `option`，也没人填 |
| 修正后仍变回默认 | 前端与后端各持一份源列表，后端推空值把前端覆盖 |
| 进度条位置错乱 | 页面**本来就有** `#dlssProgressWrap`，我又插了一套同名 id → 重复 id + 布局挤压 |
| 前置检查点了没反应 | 后端有结果，前端没有渲染分支 |

**结论**：加 UI 逻辑前，先 `grep` 目标 id——是否已存在、谁在写。

## 三、DLSS 功能的正确认知（重要，别再搞错）

**这是两条完全独立的链路：**

| | 帧生成（DLSS-G） | DLSS 5（超分/神经渲染） |
| :--- | :--- | :--- |
| 后端函数 | `NativeCore.InjectDlssG(...)` 8 参数 | `DeployDlssUnlockedToGame(gameDir)` |
| 资源 | **已内嵌在 exe**（`assets.zip` 内 `dlss/`） | 需要外部 `dlss-unlocked-standalone-*.zip`（约 600MB） |
| 需要下载吗 | **不需要** | 需要（当前无应用内下载入口） |
| 移除 | `RemoveDlssG(gameDir)` | 无内置函数，已在 `dlss.remove` 里按文件名改名为 `.hxbak` 备份 |

### `assets.zip` 内 `dlss/` 实际内容（已实测）

```
dlss/version.dll                          853 KB
dlss/dlssg_sm86.ini                         7 KB
dlss/dlssg_sm86/runtime/nvngx_dlssg.dll   7.5 MB
dlss/dlssg_sm86/backend/sm86_backend.dll  2.1 MB
dlss/dlssg_sm86/kernels/fg_kernels.dll   18.3 MB
dlss/dlssg_sm86/xefg/xefg_kernels.dll     5.4 MB
dlss/alternatives/{version,winmm,dbghelp,dinput8,dxgi,d3d12}.dll
```

`InjectDlssG` 逻辑：先用 `ResolveBestDlssRuntime()` 找本地运行库，找不到就 `GetPackagedResource("dlss/...")` 从内嵌包解出来 → **零下载可用**。

### 下拉选项（必须与老界面一致）

老界面定义在 `src/MainWindow.xaml`，取值规则是**取冒号前短值**（`TakePrefix`）：

| 项 | 可选值 |
| :--- | :--- |
| 优化等级 optLevel | `1` 全部加速(推荐) / `2` 图像内核加速 / `3` 全部有损 / `0` 原厂 |
| 插帧倍数 maxFrames | `4`(默认 4X) / `2` / `3` / `5` / `6` |
| 引擎 engine | `DLSS`(默认) / `XeSS`(仅 2X) |
| 预设 preset | `Auto`(默认) / `A` / `B` / `C` |
| 超分 srMode | `Off`(默认) / `On`(仅 RTX 30/20) |

> 曾把网页选项写成 `fsr3/pure/re`、`quality/balanced`，后端一个都不认，等于参数全废。

### 决策（用户已定）

**不做应用内运行库更新**。上游组件有新版 → 直接替换 `assets.zip` 内容 → 发软件新版本，用户更新软件即可。
因此 DLSS 页的镜像源下拉 / 检查更新 / 下载进度条已全部移除；`update.download` / `update.apply` 属于**软件自更新**，仍要做。

## 四、40HX 与 90HX 是两套机制

- **90HX**：走"通道"模式（A UEFI 直启 / B UEFI Shell 链启 / C U 盘引导 / D 恢复官方引导），入口是页面底部「引导写入安全锁 → 掀保护盖 → 立即执行固件解锁」。
- **40HX**：走**外置工具**。`NativeCore.EnsureToolkitExtracted("40hx")` 把 `assets.zip` 里的 `40hx/` 解到
  `%ProgramData%\CMP90HX_Toolbox\toolkit\40hx\`，再启动其中的：
  - `40HXCheck.exe`（查询）
  - `40HXInstaller.exe`（解锁）
  - `40HXUninstaller.exe`（卸载）
  需要提权（`UseShellExecute=true` + `Verb="runas"`）。

`assets.zip` 内 40HX 相关条目（已实测存在）：
`40hx/40HXUNLK.EFI`、`40hx/files/40HXUNLK.EFI`、`40hx/files/WinRing0x64.sys`、`40hx/40HXInstaller.exe`、`40hx/40HXCheck.exe`、`40hx/40HXUninstaller.exe`、`manual_install.bat`、`manual_uninstall.bat`、`README.md`、`ThrottleStop.sys`、`gen2/*`、`EFI应急修复指南.md`

> 另有 `50hx/50HXUNLK.EFI` 存在，但 **50HX 未验证，已上锁**（按钮置灰挂叉，后端直接拒绝）。

**两套面板必须互相隔离**（已实现 `applyUnlockCardLayout(card)`）：选 40HX 时隐藏 90HX 的四个通道、U 盘行、底部开盖解锁、顶部三个操作按钮。

## 九、验收口径（本轮踩过的坑，务必按此判定）

### 命令回执必须能区分三种情况
| 情况 | 正确回复 | 错误做法 |
| :--- | :--- | :--- |
| 成功且有数据 | `ReplyDataJson`，含 count / path 等结果字段 | 只回 `ReplyOk`，界面无反馈 |
| 成功但结果为空 | 同上，`count:0` + 说明文案（"未发现…"） | 回"失败"，或干脆不回复 |
| 执行出错 | `ReplyFail` + 错误码 + **可操作的下一步** | 吞异常后回"完成：0 个" |

**历史事故**：`dual.scanGames` 把异常吞成空列表并回"扫描完成：0 个"，
用户以为机器上真没装游戏，实际是盘掉线。已改为失败时回
`INTERNAL` + "请检查磁盘是否在线、是否有读取权限"。

### 构建门禁
- `merge-web.ps1` 缺失 → **构建失败**（否则会把上一次的 `index.html` 编进新 exe）
- 缺 Python → **构建失败**，需显式 `-SkipContractAudit` 才跳过契约检查
- 契约 `[2]`（页面等宿主从不发的事件）→ **构建失败**
- 契约 `[1]`（前端发但后端未实现）→ 只告警（当前 4 个：`dual.bind` / `dual.unbind` /
  `factory.reset` / `snapshot.restore`）
- 契约 `[3]` **不得用于门禁**——识别器只认 `case` 下一行直接赋值，9 条全是假阳性

### 前端改动如何生效
运行时不读 `web/index.html`，读的是编译时内嵌的那份。
**必须** `build.ps1`（内部先 merge 再内嵌）。手改 `index.html` 会在下次构建被覆盖。
`<meta name="hx-build">` 是构建戳，可用来确认 exe 里是哪一次合并的前端。
### 真机验收（不可用浏览器预览替代）
双卡页、解锁页、DLSS 页各在**真机**走一遍「空态」和「有数据态」。

理由：本轮至少三处问题只在真机暴露，mock 下全部自洽——

| 问题 | mock 下为什么看不出来 |
| :--- | :--- |
| 双卡「共 N 款」与「暂无绑定游戏」同屏 | MOCK 里 `boundGamesCount` 与 `boundApps` 绑死同步，永远一致 |
| `boundGames` 语义错（是 Windows 图形首选项条数） | MOCK 直接写死 2，看不出它不来自本工具 |
| `bindings` 恒为空数组 | MOCK 给的是真实数组 |

**结论：只靠预览验收，会漏掉「两个数据源语义不一致」这一类问题。**
