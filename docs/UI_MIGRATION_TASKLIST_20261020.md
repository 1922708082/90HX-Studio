## 一、技术路线：建议 WebView2 全窗口宿主

| 方案 | 视觉还原 | 单文件 | 工期 | 结构性收益 |
| :--- | :---: | :---: | :---: | :--- |
| **A. WebView2 全窗口**（推荐） | **100%** | 48MB → 约 50MB（+2MB loader） | 约 3.5 周 | **一次性消灭 238 处 FindName / 250 字段 / 1,190 行 InitEvents** |
| B. 移植为 XAML | 约 75% | 保持 | 约 6 周 | 同样要重写 12 个页面，且 `backdrop-filter` 无法实现 |
| C. 混合（WPF 框架 + WebView2 内容区） | 约 90% | 保持 | 约 5 周 | 两套渲染栈并存，最复杂，不推荐 |

**选 A 的核心理由**：这个原型最值钱的东西（毛玻璃、CSS 3D 显卡、粒子场、发光仪表）在 WPF 里**做不出来或做出来很难看**。而走 A 之后，`MainWindow.xaml`(2,664 行) 和 `App.cs` 的整个绑定层可以整体删除——这正好是我上一轮审计里 P0-3「字符串 FindName 绑定 → 功能静默失效」的根治办法，等于**用换 UI 顺手把最大的技术债还了**。

**选 A 的代价（必须接受）**：
1. 依赖 WebView2 Runtime（Win11 自带；Win10 需装过 Edge）。必须做检测 + 降级
2. WebView2 是独立进程，内存 +100~150MB
3. 首屏比原生慢 200~400ms（用骨架屏盖住）
4. `Microsoft.Web.WebView2.Core.dll` + `WebView2Loader.dll` 需随程序分发（内嵌解压，用户无感）
5. 你的目标硬件是 CMP 矿卡 —— **Chromium 有驱动黑名单，很可能禁用 GPU 加速转软件渲染**，动效会卡。这条是本方案最大风险，见 T6.1

## 五、明确不建议做的事

1. **不要把 HTML 里的 `onclick="executeSimulatedAction(...)"` 直接接到真操作上** —— 原型里这些函数是纯动画模拟，接错会误触发解锁/重置
2. **不要在 WebView2 里跑 PowerShell** —— 全部经 C# 桥接，否则等于给自己开一个远程执行口子（当前 `App.cs:439` 关 TLS 的教训已经够深刻）
3. **不要把型号表 / 密钥 / 端点写在 HTML 里** —— 用户按 F12 就能看到
4. **不要保留原型的假状态标签**（"BCD 自动回滚保护: 已启用"、"共 2 个可还原点"）—— 假绿灯比红灯更危险
5. **不要在本轮同时改业务逻辑** —— UI 迁移和逻辑重构一起做，出问题无法定位是谁的锅
